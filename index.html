Deux systèmes de rôles distincts

C'est la source de confusion numéro un. Azure possède deux systèmes de rôles indépendants : un rôle dans l'un ne donne aucun droit dans l'autre.

Pièges classiques : un Administrateur général n'a, par défaut, aucun accès aux ressources Azure (il peut toutefois s'élever en User Access Administrator à la racine). Un Propriétaire d'abonnement ne peut pas créer d'utilisateurs ni réinitialiser de mots de passe.

Plan de contrôle vs plan de données (Azure RBAC)

Les rôles comme Contributeur gèrent la ressource (plan de contrôle : Actions). Lire le contenu (blobs, secrets, messages) relève du plan de données (DataActions) et demande des rôles spécifiques comme Storage Blob Data Reader ou Key Vault Secrets User.

Attention : un rôle de plan de contrôle qui peut lister les clés d'accès d'un compte de stockage (Contributeur, Storage Account Contributor) donne indirectement accès aux données. Désactiver l'authentification par clé partagée quand c'est possible.

Bonnes pratiques

  • Moindre privilège : le rôle le plus restreint, à la portée la plus petite possible.
  • Attribuer à des groupes plutôt qu'à des personnes (pour Entra ID, le groupe doit être role-assignable).
  • PIM (Entra ID P2) : rendre les rôles privilégiés éligibles et activables à la demande, avec justification et durée limitée.
  • Unités administratives : en MSP ou multi-sites, limiter un Helpdesk Administrator à un sous-ensemble d'utilisateurs.
  • Comptes d'urgence : au moins deux comptes break-glass Administrateur général exclus de l'accès conditionnel, surveillés.
  • Identités managées pour les applications plutôt que des secrets de principal de service.
  • Revues d'accès régulières sur les rôles privilégiés.

Two separate role systems

This is the number one source of confusion. Azure has two independent role systems: a role in one grants no rights in the other.

Azure RBACEntra ID
What it controlsAzure resources: VMs, networks, storage, Key Vault, databases…The directory and Microsoft 365: users, groups, licenses, applications, Exchange, Intune…
ScopeManagement group, subscription, resource group, resource (inherited downwards)Whole tenant (/), administrative unit or application
ExamplesOwner, Contributor, Reader, Virtual Machine ContributorGlobal Administrator, User Administrator, Helpdesk Administrator
Where to assign itPortal: resource → Access control (IAM)Entra admin center → Roles and administrators
Toolsaz role assignment, New-AzRoleAssignmentMicrosoft Graph PowerShell, New-MgRoleManagementDirectoryRoleAssignment
Custom rolesYes (Actions, NotActions, DataActions)Yes, with an Entra ID P1 or P2 license
Classic pitfalls: a Global Administrator has, by default, no access to Azure resources (although they can elevate to User Access Administrator at root scope). A subscription Owner cannot create users or reset passwords.

Control plane vs data plane (Azure RBAC)

Roles like Contributor manage the resource (control plane: Actions). Reading the content (blobs, secrets, messages) belongs to the data plane (DataActions) and requires specific roles such as Storage Blob Data Reader or Key Vault Secrets User.

Warning: a control plane role that can list a storage account's access keys (Contributor, Storage Account Contributor) indirectly grants access to the data. Disable shared key authentication when possible.

Best practices

  • Least privilege: the most restricted role, at the smallest possible scope.
  • Assign to groups rather than individuals (for Entra ID, the group must be role-assignable).
  • PIM (Entra ID P2): make privileged roles eligible and activated on demand, with justification and a limited duration.
  • Administrative units: for an MSP or multiple sites, limit a Helpdesk Administrator to a subset of users.
  • Emergency access accounts: at least two monitored break-glass Global Administrator accounts excluded from Conditional Access.
  • Managed identities for applications rather than service principal secrets.
  • Regular access reviews of privileged roles.
